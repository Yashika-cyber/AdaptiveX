= AdaptiveX Study Guide
:toc:
:toclevels: 2
:source-highlighter: rouge

== In one minute

AdaptiveX is a local **order-matching simulator**, not a real exchange. The C++17 engine generates fake buy and sell orders, queues them, schedules worker threads, matches compatible prices, and produces measurements. A Python FastAPI service starts the engine and streams its JSON snapshots to a React dashboard. The dashboard can also configure, start, stop, and reset a run.

[source,text]
----
Simulated orders -> ingress queue -> dispatcher -> scheduler -> workers
   -> per-symbol order book -> metrics/WAL -> JSON -> FastAPI/WebSocket
   -> React dashboard
----

== Architecture

=== C++ engine

The engine is the simulation and measurement layer. It owns orders, scheduling, matching, cache models, the write-ahead log (WAL), and metrics. It prints one JSON snapshot per second to standard output; diagnostic messages go to standard error.

=== Python API

FastAPI launches the compiled engine as a child process, reads its output, and broadcasts snapshots to browsers over WebSocket. HTTP endpoints provide configuration and run controls. If the engine executable is missing, the server can send **demo** data; demo values are generated and are not engine measurements.

=== React dashboard

React receives snapshots through a WebSocket hook and displays values in tabs. Its control panel calls the API to save configuration and operate the simulation. The dashboard does not connect to a real exchange.

== How a run works

. `OrderGenerator::next()` creates an order and an inter-arrival delay. A fixed seed makes the random sequence reproducible.
. The generator records a routine arrival log and puts the order on the selected ingress queue.
. A dispatcher moves the order to the active policy scheduler.
. A worker takes an order, measures its time spent waiting, accesses both cache models, and submits it to the matching engine.
. `OrderBook::match()` stores the order or matches it against the best compatible order for that symbol. It reports fills to the WAL as critical records.
. The engine's main thread samples counters, queue depth, latency, fairness, cache, WAL, policy, and book data once per second.
. Each snapshot is JSON. The server broadcasts it; the React hook updates the current snapshot and recent history.

At shutdown, the engine stops generation, drains queued work, joins workers, then stops the WAL so pending records can be flushed.

== Important terms and behavior

=== Orders and order books

An **order** says buy or sell a symbol, at a price, for a quantity. A **bid** is a buy order; an **ask** is a sell order. The order book stores price levels per symbol: highest bid first, lowest ask first. If best bid >= best ask, the prices cross and a fill occurs. The fill quantity is the smaller remaining quantity; the sample executes at the resting ask price. Unfilled quantities remain in the book.

The snapshot sends the top five **aggregated** bid/ask levels for one active symbol (the alphabetically first active symbol). The dashboard computes spread as best ask minus best bid.

=== Queueing, synchronization, scheduling

The **ingress queue** is the generator-to-dispatcher handoff. `locked` uses a mutex; `lockfree` uses a bounded atomic queue of 65,536 entries. The dispatcher and policy schedulers are separate: scheduler queues remain mutex-protected in either mode.

* **Priority:** larger priority number first; arrival sequence breaks ties.
* **SJF (Shortest Job First):** smaller estimated service time first; sequence breaks ties.
* **RR / Round Robin:** in this code, FIFO order. It does *not* rotate fairly between trader groups.
* **Adaptive:** starts with FIFO/RR. It smooths scheduler queue depth using an EWMA. After three one-second checks above the high-water threshold it switches to SJF; after three checks below the low-water threshold it switches back to RR. Switching drains pending orders into the new scheduler.

The defaults are 1,000 normal arrivals/sec, 5,000 burst arrivals/sec, four workers, 20 symbols, 500 high-water, and 100 low-water. Burst mode is a probabilistic state, not a fixed timed interval.

=== Measurements

* **Throughput (`tput`):** orders workers processed per second; it is not trades/fills per second.
* **Latency (`p50_us`, `p90_us`, `p95_us`, `p99_us`):** percentiles of arrival-to-worker-pop wait time, in microseconds. They do not measure the full matching or network time. The engine sorts a rolling sample capped at 10,000 observations. The dashboard currently charts p50 and p99; p90/p95 are included in snapshots.
* **Queue length (`q_len`):** orders waiting in the active scheduler, excluding ingress and in-progress work.
* **Service ratio (`sr_hft`, `sr_retail`, `sr_mm`):** processed orders / submitted orders by trader class. This counts worker processing, not successful trades. A class with zero submissions is assigned 1.0 by convention.
* **Jain fairness (`fairness`):** a 0-to-1 summary of how equal the service ratios are; 1 means equal ratios.
* **Starvation (`starved`):** cumulative count of orders whose wait exceeded 10x the current median wait.
* **Cache hit rate:** fraction of lookups found in the simulated cache. The predictive model uses symbol frequency (EWMA) and transitions between consecutive symbols (Markov-style) to prefetch likely symbols; LRU evicts the least recently used. These are comparison models, not caches that accelerate order-book data access.
* **WAL latency / lift:** delay from log enqueue to flush for critical or routine records; lift is routine latency divided by critical latency.
* **WAL flush count (`wal_flushes`):** count of successful persisted batches, not number of records.

=== Tiny glossary

* **HFT:** high-frequency trader; one simulated trader class. **MM:** market maker; another simulated class.
* **FIFO:** first in, first out—the oldest queued order is handled first. **LRU:** least recently used—the cache entry unused for longest is evicted.
* **EWMA:** exponentially weighted moving average; a smoothed value that gives recent measurements more weight.
* **Markov-style prediction:** estimates likely next symbols from observed symbol-to-symbol transitions.
* **Mutex:** a lock that lets one thread at a time use protected data. **Atomic:** a thread-safe operation on a value without a mutex.
* **WAL:** write-ahead log; records intended to preserve events. **`fsync`:** asks the operating system to flush file data to storage.
* **API:** application programming interface; here, HTTP controls and WebSocket metrics. **JSON:** text format used for snapshots. A **snapshot** is the metrics bundle for one sampling time.
* **Percentile:** p99 is a wait time at or below which 99% of sampled waits fall; it highlights the slow tail.

=== WAL / durability

The WAL appends newline-delimited JSON records to `adaptivex.wal` in the process working directory. Arrival records are **routine** and batched (default 10 ms, up to 256 records per batch); fills are **critical** and flushed immediately. A single worker owns the file, calls `fsync` after writing, and drains queues on stop. `WAL::recover()` reads brace-shaped lines, but startup does not rebuild the in-memory order books from the file. Disk persistence is implemented, but this is a simulator's WAL, not a production database or exchange journal.

== What the dashboard shows

[cols="1,2",options="header"]
|===
|Tab / panel |Meaning

|Header
|Connection/run status, active policy, policy switch count, and a browser-page elapsed clock. The clock is not engine elapsed time.

|Overview
|Throughput, latency chart, fairness gauge, policy timeline, and simulation controls.

|Performance
|Throughput, p50/p99 latency history, policy timeline, and the same simulation controls.

|Fairness
|Jain index, trader-class service ratios, starvation count, and policy timeline.

|Engine internals
|Predictive vs LRU cache hit rates and WAL latencies, lift, persisted flush count, and a queue graphic.

|Order book
|Live symbol, bid/ask price levels and quantities, plus spread. Depth is streamed by the engine, not randomly drawn.

|Burst banner
|Appears while the generator reports burst state.
|===

The queue graphic in the WAL panel is still a throughput-based illustration; actual WAL queue depths are not sent in snapshots. The dashboard's **Simulation configuration** panel edits rates, worker count, symbol count, watermarks, synchronization mode, and policy. **Save settings** persists the API config; **Start / apply** starts a run with the draft; **Stop** stops it; **Reset defaults** restores defaults and starts again.

== File guide

=== Engine: `engine/`

[cols="1,3",options="header"]
|===
|File |Purpose / key functions

|`src/main.cpp`
|Program entry point. `parse_args()` reads CLI flags; `main()` validates configuration, creates components and threads, runs the metrics loop, emits snapshots, and coordinates shutdown.

|`include/order.hpp`
|Core `Order` and `Fill` data structures, trader/side enums, and `latency_us()`.

|`src/generator.cpp`, `include/generator.hpp`
|`OrderGenerator` validates settings, prepares symbol/price/trader distributions, `init_zipf()` weights popular symbols, `make_order()` builds one order, and `next()` handles bursts and arrival delays.

|`src/scheduler.cpp`, `include/scheduler.hpp`
|Priority, SJF, and FIFO/RR implementations. Each provides `push`, `pop`, `pop_wait`, `size`, and `drain_into`; `make_scheduler()` selects one.

|`src/controller.cpp`, `include/controller.hpp`
|`AdaptiveController::tick()` smooths queue depth and chooses RR/SJF; `switch_to()` drains pending orders and swaps scheduler. Also exposes `push`, `pop_wait`, queue size, active policy, and switch count.

|`include/sync_locked.hpp`, `include/sync_lockfree.hpp`
|Mutex queue and bounded sequence-number atomic queue for ingress; the latter exposes `try_push()` / `try_pop()`.

|`src/order_book.cpp`, `include/order_book.hpp`
|`SymbolBook::add()` and `try_match()` manage price levels and fills. `OrderBook::match()` locks the relevant symbol book; snapshot methods return levels and active symbols.

|`src/fairness.cpp`, `include/fairness.hpp`
|Counts submissions/completions, calculates each service ratio and Jain index, and detects long waits. `jains_index()` is independently reusable.

|`src/cache.cpp`, `include/cache.hpp`
|`LRUCache::access/insert()` implement recency and eviction. `PredictiveCache::lookup()` measures a hit; `observe()` learns frequency/transitions, admits the symbol, prefetches candidates, and evicts low-score entries.

|`src/wal.cpp`, `include/wal.hpp`
|`write()` queues a record; `run()` prioritizes critical and batches routine records; `flush_batch()` appends and fsyncs; `recover()` reads records; `stop()` drains; `stats()` reports counters/latencies.

|`src/metrics.cpp`, `include/metrics.hpp`
|`LatencyHistogram::record/compute()` stores and calculates percentiles; `ThroughputCounter` counts completions; `to_json()` serializes snapshots; `print_json()` writes a complete line.

|`tests/`
|Unit tests cover scheduler ordering/concurrency/draining, fairness formulas/starvation, deterministic generator behavior/rate, order-book matching/partial fills, and lock-free queue concurrency. There are no dedicated WAL or metrics tests in this test directory.

|`CMakeLists.txt`
|C++17 build, executable, CTest registration, and ASan/TSan targets.
|===

=== API: `server/`

`main.py` contains:

* `run_engine()` launches the binary, reads JSON stdout, and broadcasts snapshots; `demo_mode()` emits synthetic fallback snapshots.
* `broadcast()` sends an event to connected WebSocket clients.
* `merged_config()` combines defaults with user settings, rejects unknown keys, and checks configuration choices and selected numeric ranges.
* `start_engine()` / `stop_engine()` manage the subprocess and task.
* `GET /health`, `GET /snapshot`, `GET /config`, `PUT /config`, `POST /start`, `/stop`, `/reset`, `/restart`, and `WS /ws`.

`requirements.txt` lists Python dependencies. The server currently enables permissive CORS; use it as a local development/demo service, not an exposed production API without appropriate security controls.

=== Dashboard: `dashboard/`

* `src/App.jsx`: selects Overview, Performance, Fairness, Engine Internals, and Order Book tabs and lays out their panels.
* `src/hooks/useMetrics.js`: connects WebSocket, retains 90 snapshots of history, fetches config, and calls the control endpoints.
* `src/components/ControlPanel.jsx`: edits config and calls save/start/stop/reset.
* `Header.jsx`: status and current policy.
* `ThroughputCard.jsx`: throughput, change from prior snapshot, queue, latency, starvation.
* `LatencyChart.jsx`: p50/p99 trend.
* `FairnessGauge.jsx`: Jain index, service ratios, starvation.
* `PolicyTimeline.jsx`: recent policy durations (up to 60 seconds).
* `CacheMetrics.jsx`, `WALMetrics.jsx`: cache and WAL comparison/measurements.
* `OrderBookViz.jsx`: renders live book levels from snapshot data.
* `index.css`, `main.jsx`, `index.html`, `vite.config.js`: styling, React startup, HTML entry, and Vite development/build configuration.
* `package.json` / `package-lock.json`: frontend dependencies and reproducible npm install.

=== Experiments and build

* `experiments/configs/baseline.yaml` and `highload.yaml`: repeatable normal/high-load settings.
* `experiments/run_all.sh`: runs each configuration repeatedly with different seeds, saves JSONL runs, and aggregates a CSV summary.
* Top-level `Makefile`: `make build`, `make test`, `make server`, `make dashboard`, `make asan`, `make tsan`, and `make experiments`.

== Run it

Requirements: CMake 3.20+, a C++17 compiler, Python 3.11+, and Node.js 20+.

[source,bash]
----
# From the project root: build engine and run C++ tests
make test

# Terminal 1: API (build first)
cd server
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
uvicorn main:app --host 127.0.0.1 --port 8000

# Terminal 2: dashboard
cd dashboard
npm install
npm run dev
----

Open the Vite URL (normally `http://localhost:5173`). The dashboard defaults to `ws://localhost:8000/ws`; it can be overridden with `VITE_WS_URL` and `VITE_API_URL`.

Standalone example:

[source,bash]
----
./engine/build/adaptivex --rate 1000 --burst 5000 --seconds 10 \
  --seed 42 --workers 4 --sync locked --policy adaptive
----

== Good facts to remember

* Queueing latency is not end-to-end latency; throughput counts processed orders, not fills.
* The queue-depth control applies to the policy scheduler; the selectable locked/lock-free mode applies only to ingress.
* Cache results compare algorithms but do not currently speed up matching.
* Live order-book data and WAL file persistence are implemented; demo-mode data is synthetic.
* `RR` currently means FIFO order, not fairness across trader classes.
* The WAL file does not restore an order book on restart.
* Sanitizer targets are available, but sanitizer/runtime support depends on the platform.

== Suggested study path

. Read `order.hpp`, then `generator.cpp` to understand the data being simulated.
. Follow `main.cpp` thread creation and trace one order through ingress, scheduler, worker, and `OrderBook::match()`.
. Compare `scheduler.cpp` policies and read `controller.cpp` to understand adaptive switching.
. Trace how the engine builds JSON in `metrics.cpp`, how `server/main.py` broadcasts it, then how `useMetrics.js` and `App.jsx` display it.
. Read the focused tests under `engine/tests/`; they demonstrate expected ordering, matching, fairness, reproducibility, and concurrent queue behavior.
